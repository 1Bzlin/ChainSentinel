## 主要问题

### P0：回答引用协议失配

Graph 和 Tool 证据经常被模型输出为 `[doc:...]`，而系统要求分别使用 `[graph:...]` 和 `[tool:...]`。Review 能检测到引用错误，但当前只在答案末尾追加 `review_warning`，没有将运行状态改为失败或触发重写。

直接结果：

- 回答忠实性仅 1 / 15；
- 22 条需要特定引用类型的样例中有 13 条失败；
- `graph_001` 的查询和图路径均成功，但因引用格式错误失败；
- `mix_001` 同时发生 Graph、Tool 引用格式错误。

### P0：Secure RAG 召回不足

11 条指定 Gold 文档的检查中有 8 条没有命中。最明显的是 SUP-001 合同查询：计划和权限校验完成，但 `confidential-supplier-contract` 返回空证据。

应重点检查：

- Qdrant payload 中的 `tenant_id`、`security_rank`、`department`、`supplier_id`；
- PostgreSQL Document 与 Qdrant chunk 的 ID 映射；
- Supplier-scoped RAG 是否把正确的 PostgreSQL supplier UUID 注入过滤器；
- 文档 slug、标题和 chunk 引用 ID 是否一致。

### P0：Review 只验证引用存在，不验证论断蕴含

定向 Review 的 6 条样例全部失败。当前规则能识别部分缺失或非法引用，但不能可靠识别：

- 引用来源与论断类型不匹配；
- 从一次延迟过度概括为所有订单永久延迟；
- Graph 路径没有客户节点却声称影响具体客户；
- 旧 Memory 与新工具数据冲突时仍采用旧结论。

### P1：复杂任务拆解和动态实体传递不足

复杂编排通过率为 40%。常见失败包括：

- 多意图请求只保留一个任务；
- Graph 找到实体后，后续 Tool 任务无法消费上游实体；
- 双供应商比较任务不完整；
- 可选任务语义和 `required=false` 不稳定；
- 分析后导出、产品依赖后查风险等依赖计划被降级为澄清。

### P1：多轮上下文仍存在割裂和指代误解

上下文与 Memory 通过率为 44%。简单的单供应商“它”可以解析，但以下场景不稳定：

- 同时存在供应商和产品时的“它”；
- “前一家”“第二家”等序数指代；
- 明确切换新主题；
- 别名“主供方”；
- 旧事实与实时数据冲突；
- Memory 关闭后的计划快照仍保留已被 Validator 移除的 Memory 任务。

### P1：审计计划快照不是最终执行计划

`AgentExecutionPlan.plan_json` 保存的是 Planner 生成的校验前计划。Validator 删除或改写任务后，`plan_json` 没有同步更新。任务运行表能反映最终执行情况，但单看计划表可能误判系统执行了被禁止任务。

### P2：外部模型失败缺少稳定降级

运行后段 DeepSeek 返回两次 HTTP 402 `Insufficient Balance`：`mem_012`、`ans_013`。Runner 将其记录为失败并继续执行剩余样例，但系统没有可用的模型降级路径。这两条不属于业务逻辑失败，排除后工作流通过率为 51.94%。

另外，项目 `.env` 中 `DEBUG=release` 不是合法布尔值；本轮通过进程级 `DEBUG=false` 才能启动。

## 建议修复顺序

1. 统一 Evidence citation schema，强制 Graph/Tool/RAG/Memory 使用各自引用格式，并在 Review 失败时触发一次确定性重写或将状态置为失败。
2. 排查合同类 Secure RAG 的 Qdrant payload 与 supplier UUID 过滤，恢复 Gold 文档召回。
3. 给 Review 增加 claim-evidence entailment、时间新鲜度和来源类型一致性检查。
4. 为 Planner 增加显式的上游输出绑定，例如 `input_from: graph_1.entities.suppliers`。
5. 将上下文解析从“供应商优先”改为候选实体集合加谓词约束，无法唯一确定时必须澄清。
6. 在 Validator 完成后持久化最终计划版本，同时保留 proposal 与 validated plan 两份审计快照。
7. 增加 LLM 余额/限流探测、熔断和备用 Provider。
